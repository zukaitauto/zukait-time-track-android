# Live-status session partitioning

The live-status refresh expanded the complete session history for each employee, often twice. The candidate partitions that history by employee once, then runs the existing selection predicates and ordering against each employee's rows. It changes no business records, permissions, function signature, client payloads or workflow rules. No app update is required for the database optimization.

Native PostgreSQL 17 acceptance run 39595786464 passed with 19 employees, 7,000 synthetic sessions, 3,587,918 bytes of synthetic JSON and work_mem=2184 KiB. Median isolated refresh time was 138.267 ms before and 36.340 ms after. Median complete-save time, including production save-trigger definitions, was 171.733 ms before and 64.629 ms after. Temporary blocks written fell from 17,632 to 944. These are synthetic measurements, not production latency, physical Disk IO or billed bandwidth savings.

The tests also passed all sixteen legacy/output parity cases, complete-save payload and history preservation, the identical-save revision guard, overlapping-device CAS protection, and the existing native reception/delivery/cancellation/identity concurrency suite. The tests use only disposable loopback PostgreSQL databases and contain no production rows. Physical-device acceptance and fresh production backup restoration were not part of this database-only test.
