# Audited suppliers — inactive persistence candidate

This extends the initial recorded-payable calculation foundation with supplier identity metadata only. It is not connected to the Accountant UI/API and does not post bills, credits, openings, payments or expenses. No production source/schema/grants/accounts/flags are changed. The SQL in `experiments/accountant-suppliers.sql` is a disposable fixture, not a generated/applied migration.

`accountant/extensions/supplier_contracts.js` accepts only CREATE/UPDATE supplier name+active status or an explicit source-type/source-ID binding, with reason, device, immutable entity UUID, expected supplier revision and request UUID. It rejects actor/policy/bank/price fields in commands. Trusted server context must supply current active Accountant/Manager identity, completed first-login password state, session hash, online/current-account state and explicit enablement. Accountant and Manager are permitted by default; the new-operation role policy is configurable without changing existing ordinary rights. No Manager-only or no-self-approval rule is introduced. It reuses the existing Accountant HMAC canonical fingerprint helper with a distinct action namespace. No route imports the candidate adapter.

The private RLS-enabled schema has a disabled control row, immutable supplier IDs, append-only before/after events and immutable source associations. Current names/active status are an indexed latest-event SECURITY INVOKER view. Equal display names retain separate IDs. Renaming/deactivation never moves history or existing links. New links require an active supplier; an existing link cannot silently be reassigned, removed or merged. A future audited correction policy is required for mistaken bindings.

The command is service-only SECURITY INVOKER with pg_catalog search_path and schema-qualified business relations. It locks the existing Accountant journal advisory key first, then supplier control, verified active credentials and the unrevoked session. This shares the existing workshop_accountant_commands UUID receipt namespace with ordinary financial posting: no second ledger or retry table. It checks current role/session/enablement before historical replay. Exact actor/fingerprint/operation/entity replay returns the original result before stale revision evaluation; mismatches and legacy cash-receipt collisions fail. New commands validate strict bounded payloads and source uniqueness, append the existing receipt and metadata audit, and increment only supplier revision atomically. A failure rolls everything back, including a newly inserted identity. No cash entry is inserted and no workshop/history/live row is read or changed.

Service role has SELECT/INSERT on supplier identities/events/links and UPDATE only on control.revision. It cannot enable the feature, change configured roles, UPDATE/DELETE/TRUNCATE history or mutate IDs/links. Existing immutable triggers provide additional owner-level row/truncate protection. Ordinary anon/authenticated clients have neither private schema access nor command execution. No SECURITY DEFINER escalation or public RLS policy was added.

Tests run in the existing disposable PGlite/native PostgreSQL17 harness after all Mechanical fixtures. They cover first-login/role/offline/account/input gates, current session/disabled flags/configured Accountant+Manager roles, shared UUID collisions, exact retry, same-name separate identities, before/after audit, immutable source associations, deactivation history, injected post-event failure, revisions, append-only/RLS/ACL/view/function configuration, and unchanged workshop data/history/live/cash ledger. Native tests overlap exact retries and competing revision writers and exercise revocation-first replay denial. Fixture account IDs/passwords/session hashes and supplier references are synthetic only.

Remaining before integration: scoped bounded session-bound reader/API, source existence and authoritative purchase/receipt matching, reviewed bill/credit contracts and transactions, source-link correction/merge policy, guarded online UI and lost-ack/account-switch handling, upgrade/old-client/rollback tests, then coordinated generated migration/release approval. This candidate stores audited source associations; it does not establish that a source document exists or that a PO/return equals an invoice/credit. Partial invoices require finer reviewed receipt/source identities before activation. Opening cutover/control totals, period/tax policy and historical account attribution remain unconfirmed. The current nine-module Accountant and append-only ledger remain authoritative.
