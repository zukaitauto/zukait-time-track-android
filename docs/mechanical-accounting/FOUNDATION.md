## Inactive checklist/task transition candidate

`extensions/mechanical_rules.js` now adds pure MC registration, task creation, multiple-mechanic assignment and audited handover plans. It is not imported by any API route or UI. MC registration requires an existing active JC, a valid explicit manual JC date, configured duplicate policy and a server-verified allocated MC identity tied to the same request UUID. It does not allocate sequence numbers or create JC records. Mechanical department identity must be supplied explicitly in trusted policy; no production Jibin/department mapping is guessed.

Handover is distinct from existing REASSIGN. It requires server-confirmed closed/paused outgoing work, unchanged allocation and employee-session tokens, an inactive-free target, an explicit reason and explicit successor allocation. It marks the source assignment completed, retains its employee, suggested time and all recorded sessions, creates a linked successor assignment and records before/after attribution. It never starts a timer or silently stops running work. Task assignment only schedules work; Start/Pause/Stop remains the existing shared time authority. The prototype does not establish duty/leave/overtime eligibility for a future Start command or change labour/payroll/QC calculations.

The pure function returns dedicated scoped Mechanical record updates and shared workshop assignment updates. A future server handler MUST persist both atomically, check both revisions, enforce immutable UUID/fingerprint receipts and database constraints, and read current verified time in that same transaction. The test harness exercising revision conflicts is not a replacement for real PostgreSQL concurrency/allocator qualification. Receipt/audit arrays in the prototype input/output model scoped database projections; they must not be appended to the production full-state JSON or loaded as unbounded history.

Tests exercise separate MC/manual-JC identity, request retry/misuse, configured duplicate gating, independent tasks, multiple mechanics, wrong-department/inactive employee denial, target/source running work, changed session/allocation tokens, handed-over original session/hour preservation, reason/audit, no implicit timer start, lost-ack successor deduplication, metadata/workshop revision checks and source immutability. The allocator and command write share a transaction: lock Mechanical control then workshop row, check request receipt before stale revisions, validate both revisions, verify the proposed next display number, insert the checklist and only then advance the counter. MC/task metadata writes do not update/archive the full workshop snapshot. Numbering continues across dates; no reset operation exists.

It does not take a caller-supplied live-status override. It never changes recorded sessions. Source equality, active-work checks, legacy period review and dual revisions are rechecked inside the transaction. Source employee/history cannot be reassigned; successor links and before/after audit persist atomically. Receipt/audit UPDATE/DELETE/TRUNCATE are denied.

## Draft server boundary and stale-save guard

`extensions/mechanical_api.js` is a dependency-injected server command boundary candidate. It remains unimported by the deployed router. Both trusted enable flags default off; verified current actor and explicit capabilities are required before receipt/context reads. Client actor/policy/allocation/persistence plans and supplied history tokens are rejected. The server derives handover allocation/session checks from its authoritative snapshot, checks the expected revisions and rechecks account/role before persistence. No browser session history is needed in a command.

The receipt fingerprint now supports the stable client command before server-only time-token enrichment. The persistence adapter verifies that only those handover tokens differ. Same-request lost-ack retries resolve the stored receipt before any changed history/snapshot read; changed actor/device/payload reuse fails. Existing transition-only fixtures remain supported without changing stored receipt/RPC shape. The injected persistence implementation is not an authorization boundary by itself: atomic current-session binding in SQL and actual service-only scoped context/receipt readers are still required before routing or activation.

`experiments/mechanical-authority-guard.sql` adds separate security-invoker trigger candidates. A full-state save cannot remove linked allocations, change their employee/JC/task/checklist/predecessor/successor identity, reopen a handed-over source or alter its original allocation/completion stamp. It rejects the entire stale transaction, including prior history inserts and subsequent live-status overrides, and does not merge employee histories. Protection survives disabling new Mechanical commands. Unrelated fields and existing audited time corrections remain subject to their existing rules.

An independent live-status guard also rejects pointers to a handed-over source when the legacy RPC skips its state UPDATE for an identical submission. UUID lookups use the link primary key; legacy non-UUID assignment IDs are accepted. With no Mechanical links, the state guard returns before inspecting assignment JSON. Neither guard scans historical state JSON. These guards do not qualify every future time/QC action or prove old-client user experience: a stale client may receive a rejected save until it reloads/reconciles, so client handling and all routes still require integration tests before activation.

Tests cover default-off/no reads, role/capability isolation, spoofed envelopes/tokens, stable retry after changed history, no duplicate successor or moved hours, stale revisions, account/role changes before persistence, and real full-save RPC rollback for removed/rewritten allocations and live-status override attempts. A fresh ordinary save retaining authority succeeds. Native PostgreSQL qualification uses the existing disposable loopback-only workflow; there are no production credentials or business writes. This is an additional inactive draft step, not a released API.

Remaining next integration gates: atomically bind commands/replays to current staff session in SQL, add bounded service-only readers, connect the verified-session router only behind default-off flags, and verify legacy client conflict/reload handling, shared Start/Finish/QC permissions and concurrency. ## Default-off routed candidate and atomic session binding

The later draft now connects `mechanical_command` through `extensions/mechanical_route.js` after existing session authentication and before restricted role dispatch. Only the exact server environment value `ZUKAIT_MECHANICAL_ENABLED=true` opens the route; absent/false/other values make zero extra Mechanical database calls. The separate database settings remain disabled and unmapped. These source changes are not deployed or activated.

The adapter hashes the existing session header server-side; clients cannot supply an actor, policy, allocation, token hash or persistence plan. The service-only SQL commit requires that hash and locks the active credential row followed by the matching nonrevoked session row before checking receipts, capabilities and revisions. Locks persist through the transaction. A revocation that wins first causes a waiting command to recheck and fail; a valid command that wins first completes before revocation. Inactive/changed-role users and revoked or wrong-account sessions cannot replay existing receipts. No session expiry policy or new authentication system is introduced, and raw tokens are never passed to SQL or returned.

These experiment files remain fixture SQL, not generated/applied migrations.

## Conflict recovery and shared time qualification

The latest draft maps the two Mechanical authority trigger errors to HTTP403 with their specific code and retryable=false. Existing clients already preserve denied queues and stop automatic retries for an unchanged rejected snapshot. This prevents those guard failures becoming generic HTTP500 retry loops. Old clients do not gain the new recovery flow without loading/installing updated assets.

Updated cloud_sync.js persists a Mechanical conflict barrier across restarts and later clicks, keeps server connectivity accurate, and requires an explicit Sync before another write. Sync fetches one current snapshot and rebases only stale authority that was unchanged from the exact local merge baseline. It retains unrelated pending edits and clicks made during the refresh. Intentional allocation/source-time changes, removed history, a missing baseline, offline/storage failures or changed account/token leave the full queue blocked for Manager review; no blanket queue deletion, reset or automatic retry is used. Recovery is a client convenience; normalized SQL authority remains the security boundary. There is no new network polling or retained archive of full snapshots.

Shared Manager rules now reject reopening/reassigning/editing the original handed-over allocation or changing its disposition through time correction. Audited closed-period correction remains supported up to the handover cutoff. The SQL guard also rejects open, malformed or post-cutoff periods explicitly bound to a handed-over source; ordinary successor work remains available. It returns before scanning sessions when there are no handover sources and never reads historical workshop_state_history JSON. Ambiguous legacy periods without an assignment ID and all old-client/device combinations still require qualification before activation.
